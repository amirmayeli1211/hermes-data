# Disk reclamation on a single-root Hermes sandbox

Session-verified recipe for "the disk is full, free some space and remove the big
duplicate files". Measured on a 7.8 GB ext4 root, `/tmp` a ~996 MB tmpfs,
`HERMES_HOME=/home/user/.hermes`.

## Order of operations

1. **Survey before deleting.** `sh scripts/disk-reclaim-survey.sh` — usage, top
   consumers, cache sizes. Add `--duplicates` for the hash scan.
2. **Reclaim caches**, not duplicates (see below).
3. **Verify nothing broke** (see the end of this file).
4. **Close the loop** so it cannot recur: widen the scheduled guard.
5. **Sync** so the improved guard survives the container.

## What actually holds the space (measured)

| Target | Size | Why it is safe |
|---|---|---|
| `~/.gradle/caches` | 974 MB | Gradle module cache; `./gradlew` re-downloads |
| `~/.gradle/wrapper/dists` | 145 MB | A downloaded Gradle distribution |
| `~/.npm/_cacache` | 156 MB | Content-addressed registry cache |
| `~/.local/share/uv` | 96 MB | uv cache |
| `~/.cache/pip` | 74 MB | pip HTTP cache |
| `projects/*/build` | 16 MB | Regenerated by the next CI build |

First run reclaimed **88% → 70%** (972 MB → 2.4 GB free, ~1.43 GB total).

`~/.gradle` was the whole story. Local Android/Gradle builds are not viable on
this host (2 GB RAM — the build runs in GitHub Actions), so these caches are pure
cost. **Check whether a local build is even possible before defending the cache.**

## Why "remove the big duplicate files" is usually the wrong task

A full hash-based scan (files ≥ 1 MiB across `/home /root /opt /var /srv`,
394 files) found **8 duplicate groups totalling ~15 MB** — and every byte was
load-bearing:

- `kotlin-reflect` / `jna` / `jna-platform` / `guava` — shared between the Gradle
  distribution and Android `cmdline-tools`
- `jgrapht-core-1.5.1.jar` — twice inside Ghidra (`Features/GraphServices` and
  `Framework/Graph`)
- `setuptools-80.9.0-py3-none-any.whl` — twice inside Ghidra (Debugger + PyGhidra)

Deleting any of them breaks the owning tool for a ~15 MB gain. Report the number,
explain why it was left alone, and reclaim the caches instead. Real caches and
tool payloads are the only two categories on a host like this; there is no third
pile of recoverable disk.

## tier 2b — the guard tier that was missing

`disk-guard.sh` cleaned only inside `$HERMES_HOME`, so it never saw the hog. The
new tier runs at the same level as tier 2 (rebuildable cache = re-download cost):

```sh
DEV_HOME="${HERMES_DEV_HOME:-/home/user}"

drop_cache() {
    label="$1"; target="$2"
    case "$target" in
        ""|/|"$DEV_HOME") log "    $label: refusing to delete $target"; return 0 ;;
    esac
    [ -L "$target" ] && { log "    $label: symlink, skipped"; return 0; }
    [ -d "$target" ] || { log "    $label: absent"; return 0; }
    reclaim "$label ($(du -sh "$target" 2>/dev/null | cut -f1))" rm -rf "$target"
}

tier2_dev() {
    log "  tier 2b — developer build caches (outside \$HERMES_HOME):"
    drop_cache "gradle module cache"  "${DEV_HOME}/.gradle/caches"
    drop_cache "gradle wrapper dists" "${DEV_HOME}/.gradle/wrapper/dists"
    drop_cache "npm cache" "${DEV_HOME}/.npm/_cacache"
    drop_cache "pip cache" "${DEV_HOME}/.cache/pip"
    drop_cache "uv cache"  "/root/.local/share/uv"
    # Quoted globs: an empty match stays a literal path that fails -d,
    # so this can never rm -rf '*'.
    for b in "${DEV_HOME}"/.hermes/projects/*/build \
             "${DEV_HOME}"/.hermes/projects/*/app/build \
             "${DEV_HOME}"/.hermes/projects/*/.kotlin/sessions; do
        [ -d "$b" ] || continue
        drop_cache "project build output (${b#"${DEV_HOME}"/.hermes/projects/})" "$b"
    done
}
```

Wire it at tier-2 level and update the `check` output so the level text lists it:

```sh
tier1
[ "$level" -ge 2 ] && tier2
[ "$level" -ge 2 ] && tier2_dev
[ "$level" -ge 3 ] && tier3
```

Note `drop_cache` removes only the **cache subdirectory** (`~/.gradle/caches`),
never `~/.gradle` itself — that directory also carries `init.d/` and
`gradle.properties`, which a user may have customised.

## Harness for testing a destructive cleaner safely

Never let a first run of a rewritten cleaner meet real data.

1. Build a throwaway home on the **guarded** filesystem (not tmpfs — see trap 1)
   with fake files of known size:

```sh
SB=/root/guardtest; rm -rf $SB; mkdir -p $SB/devhome
mkdir -p $SB/devhome/.gradle/caches $SB/devhome/.gradle/wrapper/dists \
         $SB/devhome/.npm/_cacache $SB/devhome/.cache/pip \
         $SB/devhome/.hermes/projects/demo/app/build
dd if=/dev/zero of=$SB/devhome/.gradle/caches/blob bs=1M count=40 status=none
# ...one file per target...
```

2. Copy the script and **stub the destructive history tier** so the harness can
   never touch real sessions/logs/backups:

```python
src = open('disk-guard.sh').read()
i = src.index('tier3() {')
j = src.index('\n# --- safety guard', i)
open('/root/guardtest/g.sh','w').write(
    src[:i] + 'tier3() {\n    log "  tier 3 — SKIPPED (test harness)"\n}\n' + src[j:])
```

3. Run with the guard's home variable pointed at the sandbox:

```sh
HERMES_DEV_HOME=$SB/devhome sh /root/guardtest/g.sh clean --force
```

Expected: each fake target reported as reclaimed, parent directories
(`.gradle/`, `.npm/`) still present, sandbox down to a few KB, `tier 3` skipped.

### Two traps this harness catches

- **A fixture on tmpfs proves nothing.** `reclaim()` measures
  `df -P "$MOUNT"` before/after, so a sandbox under `/tmp` (its own tmpfs) shows
  "nothing to reclaim" for every target even though the files really were deleted.
  Put the sandbox on the guarded mount. Conversely, on the guarded mount a tiny
  fixture under-reports — the deletion is what the run proves, not the size.
- **An unquoted glob in a cleanup loop can expand to nothing.** `for b in $DIR/*/build`
  with no match leaves the literal `$DIR/*/build`, and a naive `rm -rf "$b"` on a
  pattern is how a cleaner eats directories it never intended to. Quote the pattern
  and gate every target on `[ -d "$b" ] || continue`.

## Never reclaim `/opt/*`

The REA analysis engines are referenced by **absolute path** from
`mcp_servers.rea.env` (`GHIDRA_INSTALL_DIR=/opt/ghidra`,
`REA_JADX_MCP_JAR=/opt/jadx-headless-mcp/...`, `REA_APKTOOL_COMMAND`, …). A disk
sweep that deleted `/opt/rizin` left `/usr/local/bin/rizin` a dangling symlink,
and REA then reported a *launch* failure (`ENOENT`) rather than a missing tool —
`ls -la` on the symlink still looked fine. Detect with `readlink -f` / `[ -x ... ]`,
never with `ls`, and keep `/opt` out of every reclaim list.

## Delivered artifacts are scratch and get reaped

`$HERMES_OFFLOAD_ROOT/downloads` is scratch, not storage: the offload reaper
deletes anything not touched inside its window (`offload.sh`, the
`for d in tmp downloads clones` loop). An APK delivered to the user from that
directory was silently gone a few hours later — and it was the only local copy,
because the build itself had run in CI.

- Copy a file out of the offload tree before promising it will still be there, or
  point the user at the durable copy (a CI artifact, the repo).
- When a file you expected turns up missing after *any* cleanup, check the scratch
  reaper before assuming your own delete removed it — reporting a wrong cause
  sends the next debugging pass in the wrong direction.

## Verify after a reclaim

```bash
df -h /                                   # the headline
sh ~/.hermes/scripts/disk-guard.sh check  # level should now be OK
source /root/rea-tools.sh && rea doctor --client hermes   # healthy / environment_healthy
for t in /opt/ghidra/support/analyzeHeadless /opt/apktool/apktool \
         /opt/rizin/bin/rizin /usr/bin/tshark /usr/bin/objdump; do
    printf '%-50s %s\n' "$t" "$([ -x "$t" ] && echo OK || echo MISSING)"
done
find ~/.hermes/projects -name '*.kt' -o -name '*.kts' | wc -l   # sources intact
df -h /tmp                                # tmpfs is separate; check it too
```
